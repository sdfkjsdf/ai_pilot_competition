Behavior Tree (BT) Design Guidelines

These guidelines specify design requirements for behavior-tree entry conditions, node responsibilities, and command authority.

01Parent and child conditions02Selection coverage03Separation of responsibilities04Single command authority05Cyclic reevaluation
01

Parent and child conditions

Parent entry conditions shall cover
all situations requiring child maneuvers.

1-1The parent condition shall be satisfied whenever a child maneuver is required.

Example scenarioAn enemy firing threat is detected before any hit is received, requiring preemptive evasion.

Incorrect · Entry blocked by the parent condition

Firing threat present · No hit received
Parent defense condition: hit receivedCondition false → Branch blocked
Child evasion condition: firing threat presentNot evaluated

The parent entry condition does not cover a situation that requires the child evasion maneuver.

Correct · Coverage of child entry conditions

Firing threat present · No hit received
Parent defense condition: firing threat OR hit receivedCondition true → Branch entered
Child evasion maneuver selectedEvasion command generated

The parent defense branch remains reachable when preemptive evasion is required.

Figure 1-1. Coverage of child entry conditions

1-2Parent and child nodes shall use a common assessment result to avoid applying different criteria to the same situation.

Example scenarioParent and child nodes assess the same enemy firing threat.

Incorrect · Independently defined criteria

Same enemy firing situation
Parent: assess current aim onlyNo direct aim yet → Entry rejected
Child: also assess anticipated firing threatEvasion required, but node unreachable

Different criteria produce inconsistent assessments of the same threat.

Correct · Shared assessment result

Common firing-threat assessmentAssess current and anticipated threats using one set of criteria
Parent node: use the shared resultEnter the defense branch
Child node: use the same resultSelect an evasion maneuver

Parent and child nodes refer to the same threat assessment result.

Figure 1-2. Shared assessment result

02

Selection coverage

Gaps in decision-making and control commands
shall be prevented.

2-1For each situation, at least one decision module and one maneuver module shall be selectable.

Example scenarioNeither the ownship nor the opponent has a confirmed unilateral advantage.

Incorrect · Missing situation classification

No unilateral advantage
Neither offensive advantage nor defensive disadvantageNo branch defined for this situation
No maneuver selectedControl-command gap

Maneuver selection stops when the decision branches do not cover all relevant situations.

Correct · Defined selection path for each situation

No unilateral advantage
Classify as HABFMEvaluate maneuver conditions within that mode
Select one HABFM maneuverGenerate a control command

Provide a reachable path from situation classification to maneuver selection.

Figure 2-1. Defined selection path for each situation

2-2Exception handling shall not be used to bypass defects during development. The causes of exceptions shall be identified and removed through debugging before operational use.

Example scenarioA zero-magnitude error vector is supplied to a direction-error normalization calculation.

Incorrect · Underlying cause left unresolved

Direction-error vector = 0Already aligned with the target direction
Divide the error vector by its magnitudeDivision by zero
Continue execution through exception handlingCalculation and command-generation defects remain

Continuing execution through exception handling does not correct the defective calculation.

Correct · Cause removed before operational use

Reproduce the zero-error input during development
Define the calculation for the aligned stateNo normalization; direction-error rotation correction = 0
Verify generation of a valid control commandUse operationally after removing the cause

Account for the physical meaning of zero error and eliminate the undefined calculation.

Figure 2-2. Cause removed before operational use

03

Separation of responsibilities

Service, Condition, and Task responsibilities
shall be separated and observed.

3-1Services shall perform observation, Conditions shall perform assessment, and Tasks shall generate commands.

Example scenarioObservation, assessment, and command-generation functions for a climb maneuver are assigned to BT nodes.

Incorrect · Mixed node responsibilities

ServiceObserves and generates a climb command
ConditionDetermines that the maneuver is not required
Task not selectedThe Service-generated command remains

Command generation by an observation node separates command issuance from maneuver selection.

Correct · Separated node responsibilities

ServiceUpdate observed speed, range, and other state variables
ConditionDetermine whether the maneuver is required
TaskGenerate the selected maneuver command

Assign observation, assessment, and command generation to their respective nodes.

Figure 3-1. Separated node responsibilities

3-2Observed quantities shall be calculated once and shared.

Example scenarioMultiple nodes use the range to the opponent within one control cycle.

Incorrect · Repeated calculation of observations

Node A: calculate rangeUse the current sample
Node B: recalculate rangeUse a separately updated sample
Inconsistent values within the same cycleSelection and command generation use different inputs

Independent calculations and sample updates can produce different values for the same quantity.

Correct · Shared observation values

Service: acquire the current sample
Calculate and store range onceCommon observation for this control cycle
All nodes refer to the same valueSame sample and calculation result

Each node uses the common observation calculated for the current control cycle.

Figure 3-2. Shared observation values

3-3Conditions and Tasks shall use the same entry assessment result.

Example scenarioA Condition approves High-Yo-Yo entry and passes the result to the Task.

Incorrect · Approval and execution use different results

Condition: approve using the current assessment
Task: use the previous cycle's assessmentCurrent approval result not received
Selected climb maneuver not executedAssessment and execution are inconsistent

Condition approval and Task execution depend on different assessment results.

Correct · Consistent transfer of approval

Condition: approve using the current assessment
Pass the approval result to the TaskResult from the same control cycle
Task: execute the approved maneuverGenerate the climb command

The Task uses the assessment result of the Condition that selected it.

Figure 3-3. Consistent transfer of approval

3-4Additional entry conditions shall not be introduced inside a Task.

Example scenarioAll entry conditions shown in the tree are satisfied, but the Task contains an additional condition.

Incorrect · Additional entry condition inside the Task

Condition: approve maneuver entry
Task: check a separate range conditionAdditional condition not shown in the tree
Reject execution when the extra condition is falseApproved maneuver is blocked

Hidden Task conditions obscure the actual criteria for maneuver entry.

Correct · Explicit placement of entry conditions

Place required entry conditions in the Condition nodeReview the need for each condition at this point
Condition: evaluate all entry conditions
Execute the Task when approvedGenerate the command without another entry assessment

Complete entry assessment in the Condition; the Task executes the approved result.

Figure 3-4. Explicit placement of entry conditions

3-5Diagnostic nodes shall not be assigned command authority.

Example scenarioA diagnostic node detects missing diagnostic data while recording the status of a tactical command.

Incorrect · Diagnostics modify a command

Tactical Task: generate a tracking command
Diagnostic node: some logging data are missingUse the diagnostic issue as a reason to change the command
Diagnostic node substitutes a climb commandAn unselected function exercises command authority

Command replacement by diagnostics can initiate a maneuver unrelated to tactical selection.

Correct · Diagnostics restricted to recording

Tactical Task: generate a tracking command
Diagnostic node: record the missing-data statusDo not change command values
Deliver the tracking commandRetain the selected Task's command authority

Diagnostic nodes observe and record; they do not generate or modify commands.

Figure 3-5. Diagnostics restricted to recording

04

Single command authority

Exactly one module shall hold
final command authority.

4-1Modules with similar entry conditions shall be reviewed for duplication.

Example scenarioTwo registered evasion modules respond to the same firing threat.

Incorrect · Duplicate selection and command issuance

Same firing threat detected
Evasion A and Evasion B selected independentlySimilar conditions applied separately
Commands from A and B issued simultaneouslyDuplicate final command authority

Adding similar modules without distinct roles can create duplicate command authority.

Correct · Single selection after duplication review

Compare the roles and conditions of both modulesIdentify functional duplication
Consolidate duplicate functions or define selection priority
Select and issue commands from one evasion moduleSingle final command authority

Resolve duplicate functions and limit final command issuance to one module.

Figure 4-1. Single selection after duplication review

4-2When the selected module changes, the previous module shall be verified to relinquish command authority.

Example scenarioHigh-Yo-Yo ends and control transitions to precision tracking.

Incorrect · Authority retained by the completed module

High-Yo-Yo completion detected
Precision-tracking module selectedPrevious climb-command issuance remains active
Climb and tracking commands overlapPrevious module retains command authority

Selecting a successor does not by itself release the previous module's command authority.

Correct · Release and transfer of authority

High-Yo-Yo completion detected
Previous module relinquishes command authorityStop issuing commands from that module
Transfer control to precision trackingIssue one tracking command in the same cycle

Connect authority release to successor command generation to prevent overlap and gaps.

Figure 4-2. Release and transfer of authority

4-3The safety module shall relinquish command authority when a safe state has been restored.

Example scenarioThe safety module's recovery-completion conditions are satisfied after terrain-collision avoidance.

Incorrect · Continued preemption after recovery

Safety recovery complete
Safety module remains activeCommand authority not released
Climb command continuesReturn to tactical maneuvering is blocked

Retained safety authority can prevent tactical recovery after the hazard has been resolved.

Correct · Authority released on recovery completion

Confirm safety recovery is complete
End the safety maneuver and release command authority
Select a tactical module for the current situationResume tactical maneuvering

Release authority when recovery is complete and reselect tactics for the current situation.

Figure 4-3. Authority released on recovery completion

05

Cyclic reevaluation

A Reactive BT shall reevaluate from the top
of the tree in every control cycle.

5-1Guaranteed success through maneuver completion shall not be required as an entry prerequisite.

Example scenarioEvasion is currently required, but the opponent's future maneuvers cannot be determined.

Incorrect · Advance guarantee of completion success

Evasion currently required
Require guaranteed success through completionFuture opponent maneuver uncertain → Reject
Required evasion not executedEntry blocked

Requiring guaranteed future success can prevent selection of a currently required maneuver.

Correct · Current assessment and cyclic reevaluation

Select evasion using current observations
Execute the command and enter the next control cycle
Reevaluate from the top of the treeContinue, transition, or end according to the current situation

Execute the currently required maneuver and use updated observations to determine the next action.

Figure 5-1. Current assessment and cyclic reevaluation

5-2Excessively conservative entry conditions shall not prevent a required node from executing.

Example scenarioA common threat assessment identifies a need for evasion, but additional observers are required to reconfirm the same threat.

Incorrect · Accumulation of redundant confirmations

Common threat assessment: evasion required
Require simultaneous confirmation from observers A and BAdd conditions that prove the same threat again
Reject entry if either confirmation is unavailableRequired evasion is repeatedly blocked

Redundant confirmation unrelated to maneuver necessity can make a node effectively unreachable.

Correct · Retain necessary entry conditions

Review the purpose of each condition
Remove redundant confirmation of the same threatUse conditions that establish maneuver necessity
Execute the node when evasion is requiredPerform the maneuver using current observations

Review each entry condition and remove unnecessary barriers to execution.

Figure 5-2. Retain necessary entry conditions
